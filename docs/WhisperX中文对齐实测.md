# WhisperX 中文对齐实测

日期：2026-10-24。结论：可用。推荐做法是用 WhisperX 的中文模型，把已知配音文案直接对齐到配音，对齐前先把数字换成中文读法：
- 汉字处的小句边界中位误差 38 毫秒，90% 在 136 毫秒以内，最大 297 毫秒；
- 整段起止中位误差：合成语音 14 毫秒，真实配音 50 毫秒；真实配音里的停顿全部找到；
- 只用 CPU，每分钟配音约 2–3 秒处理完。

弱点在英文品牌名和型号：中文模型认不出英文发音，相邻边界中位误差 165 毫秒，最大 0.4 秒。转写类做法都比实时还慢，也没有更准。

## 测什么

计划 A1 的“语音级精确对齐”要在配音生成后自动拿到逐字时间，让字幕时间从估算变成实测。本轮先实测三件事：对齐准不准；数字和品牌名能不能处理；在这台 Mac 上跑得多快、占多少空间。

对比四种做法：

| 做法 | 说明 | 依赖 |
| --- | --- | --- |
| WhisperX 转写＋对齐 | faster-whisper large-v3 转写，再用中文 wav2vec2 模型对齐到字 | PyTorch、WhisperX |
| WhisperX 强制对齐（原文） | 不转写，直接把已知文案对齐到音频，数字原样保留 | PyTorch、WhisperX |
| WhisperX 强制对齐（数字转读法） | 同上；对齐前把数字换成中文读法，例如 1999 读作“一千九百九十九”，年份逐位读，结果再映射回原文 | PyTorch、WhisperX |
| faster-whisper 词级时间戳 | 项目现有依赖，转写时打开 word_timestamps | 无新增 |

## 测试集

三组都是中文，全部在本机生成或取自本机已有文件。本轮 AI API 调用为 0。

| 组 | 内容 | 真实时间从哪来 |
| --- | --- | --- |
| 合成整句 | 系统自带的两个中文语音（婷婷、美佳）各读 8 句广告词和 1 句带停顿的话，共 18 段、88 秒。句子里有价格、年份、分贝、型号等数字，还有中英文品牌名 | 每段的发声起止由能量检测得出；停顿句中插入的 0.8 秒停顿位置已知 |
| 合成小句 | 同样 8 句话，每句按逗号拆成小句分别合成，再用 0.25 秒间隔拼起来，共 16 段、34 个小句、77 秒 | 每个小句的起止都已知 |
| 真实配音 | 一个本机工程里 MiMo TTS 生成的 10 段分镜配音，共 24 秒 | 能量检测得出发声起止和 4 处段内停顿 |

系统自带的另外几个中文语音（Reed、Eddy、Flo）在这台机器上不读汉字，只读出了句中的英文和数字，所以没有采用。

## 怎么算误差

- 三种做法统一以汉字为锚点：每个小句取首字的开始时间和末字的结束时间，和真实起止相减。转写类做法先按字序列匹配，把转写结果对应回原文。
- 起止误差：整段第一个字的开始、最后一个字的结束，和发声起止相减。
- 停顿边界：在真实停顿处找时间上重叠最多的相邻两字间隙，比较两侧边缘。
- 数字和品牌名：转写类做法统计 15 个预期写法（如 1999、XT60、HomeKit、华为）被原样识别出来的比例；强制对齐统计数字和英文字符拿到时间的比例。

## 结果

误差都按“预测时间 − 真实时间”计算，单位毫秒，格式为“中位 / 90% 分位 / 最大”；括号里是超过 200 毫秒的个数。转写类做法有 4 个锚点因转写错字没能对上，所以汉字边界少几处。

**合成小句：34 个小句、68 个边界，真实时间精确已知**

| 做法 | 汉字边界 | 数字边界（4） | 英文边界（4） | 处理耗时 / 音频时长 |
| --- | --- | --- | --- | --- |
| WhisperX 转写＋对齐 | 51 / 160 / 982（5 处，共 56） | 687 / 777 / 816（4） | 1031 / 1041 / 1622（4） | 1.31 |
| WhisperX 强制对齐（原文） | 40 / 204 / 803（7 处，共 60） | 20 / 20 / 194 | 165 / 174 / 421（1） | 0.036 |
| **WhisperX 强制对齐（数字转读法）** | **38 / 136 / 297（5 处，共 60）** | 22 / 23 / 194 | 165 / 174 / 281（1） | **0.035** |
| faster-whisper 词级时间戳 | 210 / 310 / 380（30 处，共 56），整体偏早 183 | 580 / 620 / 650（4） | 1055 / 1150 / 1200（4） | 1.43 |

**整段起止**

| 做法 | 合成整句（汉字边界） | 真实配音（汉字边界） |
| --- | --- | --- |
| WhisperX 转写＋对齐 | 31 / 61 / 798 | 39 / 89 / 322 |
| WhisperX 强制对齐（原文） | 18 / 50 / 815 | 50 / 130 / 339 |
| **WhisperX 强制对齐（数字转读法）** | **14 / 40 / 60** | 50 / 130 / 339 |
| faster-whisper 词级时间戳 | 130 / 260 / 370，整体偏早 121 | 110 / 260 / 310，整体偏早 128 |

**停顿**

| 做法 | 真实配音的 4 处停顿 | 合成句中 0.8 秒的数字静音 |
| --- | --- | --- |
| WhisperX 转写＋对齐 | 找到 3 处，边缘误差 87 / 113 / 170 | 一个声音偏 0.7 秒，另一个没找到 |
| WhisperX 强制对齐 | 全部找到，边缘误差 73 / 92 / 184 | 没找到 |
| faster-whisper 词级时间戳 | 一处都没找到 | 找到，但整体偏早 0.2–0.3 秒 |

合成句里的停顿是纯数字静音（全零采样），强制对齐会把相邻字的时间连起来跨过去。真实配音的停顿里带底噪，字的边界会落在静音两侧。所以句内停顿以能量检测为准，对齐只用来定位停顿在哪两个字之间。

**转写质量**：合成语音的汉字错误率 7–8%，真实配音 1.1%。15 个预期写法（价格、年份、型号、品牌）里，有 26–28/30 次被原样写出。强制对齐不转写，没有这项。

**数字和英文的处理**：中文对齐模型的词表里没有数字，WhisperX 3.8 会把数字、英文这类字符当“通配”来对齐，所以原样的数字也能拿到大致时间。把数字换成中文读法后（1999 →“一千九百九十九”，年份逐位读），数字本身和相邻汉字都更准：汉字边界的 90% 分位从 204 降到 136 毫秒，最大误差从 803 降到 297 毫秒。英文单词没有对应的中文读法，误差仍然偏大。

## 安装与资源

- 单独的虚拟环境在系统盘：`~/Projects/_eval/whisperx/.venv`，1.3 GB。包含 WhisperX 3.8.6、PyTorch 2.8.0、faster-whisper 1.2.1，不进项目环境，也不进仓库。
- 模型和数据都在外接盘：
  - 转写模型复用 `111/程序文件/models` 里已有的 faster-whisper（large-v3 3.1 GB）；
  - 中文对齐模型 `jonatasgrosman/wav2vec2-large-xlsr-53-chinese-zh-cn` 下载了 safetensors 格式，1.3 GB，放在 `_dev/models/`；
  - NLTK 分句数据也放在 `_dev/models/`，已按官方索引核对过 MD5 和 SHA-256。
- 测试音频、评测脚本和结果放在外接盘的 `_dev/eval/whisperx/`，可以用评测环境重跑。

## 结论与下一步

- 配音的文案是已知的，不需要转写。转写类做法在这台 Mac 上都比实时还慢（1.3–2.7 倍），还会带进错字。faster-whisper 自带的词级时间戳整体偏早 120–180 毫秒，也找不到停顿，不适合用来定字幕时间。
- 建议接入方式（计划 A1 第三项）：
  1. 每个镜头的配音生成后，用强制对齐取逐字时间。对齐前把数字换成中文读法，结果映射回原文，按句读切成分句字幕，标记为“实测”。
  2. 对齐放在单独的进程里，用单独的 Python 环境，不把 PyTorch（约 1 GB）塞进主程序。环境和模型没装好、外接盘没插或对齐失败时，回退到现在的按字数估算，并提示“估算”。
  3. 首尾是英文的分句，边界吸附到能量检测找到的最近静音；吸附不上时提示复核。
  4. 第四项“句内停顿”以能量检测为准，再用对齐结果标出停顿在哪两个字之间。
- 未覆盖：真人语音；Windows；带数字和英文的 MiMo 配音（本轮 10 段真实配音里没有）；单段超过 15 秒的长配音。
